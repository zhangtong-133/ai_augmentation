# Scheduler 第二阶段：租约领取与幂等站内提醒投递

已接入内部领取/投递仓储和 `apps/scheduler` 后台进程。仅处理已按 [一次性提醒协议](sprint-3-scheduler-store.md)精确批准的 `local-reminder-once-v1` 任务，写入当前用户的站内提醒表。没有模型调用、工具执行或外部通知。已接入 [HTTP 管理、提醒列表和页面](sprint-3-scheduler-app.md)，数据库中的 `delivered` 表示提醒已经持久化，不代表用户已读。

## 领取与租约恢复

调度使用数据库时钟，按计划时间、用户和请求 UUID 查找已到期的 `scheduled` 或租约过期的 `running` 任务。已批准任务即使在进程停机期间到期，重启后仍会投递；未批准草稿及未来任务不会领取。

领取事务先对用户行执行 `FOR UPDATE SKIP LOCKED`，跳过被其他进程锁住的用户，再锁定任务行并重新读取状态。此顺序与批准、取消、投递和用户删除兼容。事务逐项复核协议版本、内容指纹、原批准时间处于原授权窗口、精确执行时间、单次上限和零金额确认。无效授权转为 `failed`，不投递；该轮扫描结束，下一轮继续处理其他任务。

有效领取生成随机 `claim_id`，状态转为 `running`，租约 60 秒。只有提交成功才返回内部租约凭据。进程在领取后退出或数据库异常时，其他进程可在租约过期后重新领取，生成新凭据。旧凭据永远不能完成新租约的任务。租约不是给用户的授权令牌，不能通过公共接口传入；投递不接受调用方提供的标题或正文，也不信任调用方传回的租约时间。

## 原子投递与取消语义

投递按用户、任务锁顺序重新读取，检查当前租约 ID、数据库中的租约截止时间、到期时间、任务状态和完整持久化授权。只从冻结任务读取提醒内容。提醒表以 `(user_id, request_id)` 为唯一键，插入提醒和把任务改成 `delivered`、记录投递时间在同一事务内提交。

提交失败不会留下半条提醒或错误完成状态。提交成功但响应丢失时，同一租约重试只读取已有提醒；其他进程扫描不到已完成任务。旧租约重试仍失败。由于本步骤只有同库写入，可以安全恢复；此机制不能直接用于需要外部副作用的模型、邮件或 Webhook。

取消待执行或领取中的任务会清除租约，后续投递失败。取消先拿到用户锁时不会再产生提醒；投递先提交时，取消返回原 `delivered` 状态，不伪称取消成功，也不撤回已经保存的提醒。完成任务的批准重放同样返回原终态，不重新执行。授权或内容校验失败会进入 `failed`，只可取消，不能重新批准。

`list_schedule_reminders` 是内部按用户查询接口，每页 20 条，按请求 UUID 排序，游标规则与任务列表一致。不存在跨用户读取，用户删除级联清理任务与提醒。提醒当前随任务保留，尚无已读、单条删除和归档功能。

后续已接入[每日定时日报](daily-brief-schedule.md)，local 模式也处理用户明确启用的日报配置；默认仍关闭。

## 启用与进程行为

追加 `0022_schedule_delivery.sql`，扩展任务状态和租约/投递字段，创建站内提醒表及待领取索引。先由 API 或部署流程完成迁移；Scheduler 使用 `connect_existing`，不执行迁移，不组装模型、缓存或网络通知适配器。

- `SCHEDULER_MODE=disabled` 为默认值：不连接数据库，不处理任务。
- `SCHEDULER_MODE=local`：连接 `DATABASE_URL`，投递已批准的站内提醒，并处理用户显式启用的定时日报。其他值和非 UTF-8 模式拒绝启动。
- `RUN_FOREVER=1`：循环运行，每批最多处理 100 个任务，正常批次后等待 2 秒，数据库错误后等待 5 秒；等待期间支持终止。未设置时只运行一个批次，错误返回非零退出码。

```sh
# DATABASE_URL 已指向完成迁移的数据库
SCHEDULER_MODE=local cargo run -p scheduler
SCHEDULER_MODE=local RUN_FOREVER=1 cargo run -p scheduler
```

Compose 的 scheduler 服务传递 `SCHEDULER_MODE`、`RUN_FOREVER=1` 和 `DATABASE_URL`，默认仍禁用。服务启动只等待 PostgreSQL 健康，不依赖 Redis，也不再传递未读取的 `APP_ENV`、`RUST_LOG` 或 `REDIS_URL`。进程支持 Ctrl-C 和 Unix SIGTERM：停止正在等待的批次，未提交事务回滚，已提交租约后续可恢复。首次数据库连接失败会退出，由部署进程管理器重启；已连接后的批次错误在循环模式下退避重试。缺少新迁移时不执行任务，等待部署完成后下一批重试。

日志仅输出批次投递数量和脱敏错误，不记录用户 ID、提醒内容或连接凭据。禁用并重启进程会停止后续领取，已提交的提醒不会撤回；要撤销单个未完成任务，应走持久化取消协议。
