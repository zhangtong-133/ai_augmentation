# Scheduler 第一阶段：一次性提醒授权与任务仓储

本阶段实现内部 `ScheduleStore`、授权指纹和 PostgreSQL 持久化。首个任务类型固定为 `local-reminder-once-v1`：在指定 UTC 时间生成一条站内提醒，内容由用户提供，最多执行一次，模型、工具和外部通知费用为零。当前尚未接入领取、提醒投递、HTTP 或页面，`apps/scheduler` 仍是空壳，不会自动执行已批准任务。

未来模型/工具定时任务必须另设协议和逐次费用授权，不能复用当前零费用授权，也不能自动复用一次性 Agent 批准。Cron、重复执行、外部收件人、Webhook、shell 和模型生成任务不在当前接口内。

## 不可变任务与精确确认

创建时传入 `request_id`（UUID）、标题（1–80 字符）、正文（1–2000 字符）和 `run_at_unix_ms`，拒绝空白或 NUL。身份来自调用方受信任上下文，不能从任务正文提供。首次创建时间必须在数据库当前时间之后 1 分钟至 365 天内；使用 UTC 毫秒绝对时间，不在数据库解释本地时区或夏令时。

创建只保存 `draft`，不代表授权。SHA-256 指纹绑定规范化后的用户 UUID、请求 UUID、协议版本、原始标题/正文、执行时间、最大执行次数 1 和金额上限 0。预览授权窗口为创建后 15 分钟与执行时间两者较早者。过期草稿读取为 `expired`，批准事务再次检查数据库时间，不能用客户端时间延长窗口。

批准必须提供完整 `ScheduleApproval`：相同指纹、精确执行时间、`accepted_max_runs=1`、`accepted_amount_micro=0` 和 `acknowledge_schedule=true`。事务复核保存内容的指纹，保存批准内容与首次批准时间，再转为 `scheduled`。未提交成功不能向调用方返回授权成功。同一有效批准重放保留第一次批准时间；即使预览窗口后来过期，既有授权仍可读取，重放不会延长时间或启动执行。

时间与正文不可编辑。用户要修改任务，先取消旧任务，再用新请求 ID 创建及确认新预览。相同用户/请求 ID 和相同内容重试返回原记录（包括过期、已取消状态）；不同内容报冲突。不同用户允许使用相同请求 UUID，归属和指纹独立。

## 取消、并发与边界

`cancel_schedule` 只接受归属用户的任务 ID。草稿、过期草稿和待调度任务均可取消，重复取消保留首次取消时间和既有批准凭据。取消后重新批准失败，同一创建请求不能复活任务。

创建、批准和取消均先锁定用户行，之后访问该用户任务。并发创建同 ID 只保留一条；创建配额检查与插入原子完成。批准和取消并发时，无论哪方先取得锁，取消返回后持久化状态均为 `cancelled`。用户删除通过外键级联清理全部任务；任务不绑定对话，删除对话不取消独立提醒。

目前每用户滚动 24 小时最多创建 100 条，总保留最多 1000 条（包括取消/过期记录），在既有请求重放之后检查配额。取消不释放创建额度，防止取消/重建绕过限制。本阶段不提供物理删除或自动清理，避免幂等 ID 被重用；后续归档方案需保留取消和幂等语义。所有查询均按用户隔离，列表按请求 UUID 排序，每页 20 条，`next_cursor` 是最后一个请求 UUID；分页不是跨请求固定快照。

## 迁移与后续执行契约

追加 `0021_schedules.sql`，保存不可变任务、授权 JSON、状态及时间，建立用户创建时间索引和待执行时间部分索引。没有环境变量或现有费用账本变更；创建和批准不占用模型/工具预算。

下一步实现后台领取、租约及幂等站内提醒投递。领取必须复核持久化授权、协议和未取消状态；租约过期的恢复不能重复生成提醒。投递与终态应在同一数据库事务内完成，并以用户/任务 ID 唯一约束防重。取消和投递需明确同一锁顺序及已投递语义。当前 `scheduled` 仅表示授权已保存，不能解释为已投递。

后续 HTTP 入口需沿用会话身份和 CSRF 检查，前端负责本地时间到 UTC 的明确展示与转换，毫秒和金额输出应遵循精确字符串约定。此仓储协议不直接暴露为公共 API。

授权指纹单元测试覆盖归属、请求、时间及正文变化。真实 PostgreSQL 测试覆盖并发创建/批准、跨用户查询及取消、不同内容冲突、精确确认、过期/篡改拒绝、重连持久化、取消/批准竞争、取消后重放、用户删除、时间边界、原子配额与分页，以及延迟提交失败时草稿/授权完整回滚。所有模型和外部通知均不调用。
