## HTTP 与后台执行（已实现）

- `GET /api/conversations/{id}/replies`：返回 `{enabled, mode, items}`，按创建顺序列出最多 100 个请求（对话本身最多 100 个），不返回冻结上下文。空列表也先核验归属，关闭夹具时仍可查询历史；供刷新页面后恢复历史与确认未收到响应的请求。无新迁移。
- `POST /api/conversations/{id}/replies`：正文 `{"request_id":"UUID","expected_revision":1}`，返回 202 和请求状态。同键重放仍返回 202（可能已是终态），不会再次执行；未知字段或客户端模型配置均拒绝。
- `GET /api/conversations/{id}/replies/{request}`：返回 200，字段为 `request_id`、`revision`、`status`、`output` 和 `mode: "fixture"`；不返回冻结上下文或系统提示。首次请求 ID 应由客户端保留，用于查询和原请求重试。
- `POST /api/conversations/{id}/replies/{request}/cancel`：返回当前状态，终态不撤销。全部操作要求登录，写操作还要求 CSRF 请求头；成功响应 no-store。未登录 401、CSRF 403、无归属/已删除 404、版本/额度冲突 409、非法版本 400、JSON 非法或未知字段按解析状态返回，创建未启用 503。Next.js 与 Nginx 两入口均可用。
- 禁用模式拒绝创建、不领取 queued，但仍允许查询/取消旧请求和清理过期派发。开启 fixture 后会恢复尚未领取的持久化队列。请求断开不取消已预留任务，须显式取消。
- 后台每轮最多扫描 20 项，优先处理超过 120 秒的 dispatching，再处理 queued；串行执行后等待 1 秒。多实例共用数据库单次领取，不自动重试生成。仅接受固定 `builtin-fixture/fixture-v1` 配置，其他配置失败，不转发供应商；完成写回失败后由过期扫描收敛为 unknown。扫描或写回故障只记录脱敏告警。
- 内置夹具等待 100 毫秒后回显最后一条冻结用户消息，并附测试标记，仅用于验证生命周期，不代表理解历史或遵循模型输出 token 限制。关闭进程后，已领取请求只会过期，不重新生成。没有供应商请求超时、重试或计费路径。

## 上下文规则（已实现）

- 调用方须读取当前用户有权访问的 PostgreSQL 消息快照；规划器本身不认证，也不读取 Redis。请求固定 `expected_revision`，不匹配拒绝执行，不能因后续消息改变原请求内容。
- 仅接受现有完整用户消息快照：未删除、版本等于条数、最多 100 条、序号从 1 连续递增；所有正文均通过现有 4096 字节/非空/NUL 校验，包括被省略的旧消息。空对话拒绝回复。
- 固定服务端系统提示，加最新连续用户消息后缀，最多 16 条；所有正文连同系统提示最多 16 KiB UTF-8。整条保留，遇到容量不足即停止，不跳过中间消息、不拆分 Unicode。返回版本、首条序号、省略条数和实际字节数，供持久化与页面说明使用。
- 所有持久化消息映射为 `user`；正文中的角色标记不能变成系统指令角色。不注入长期记忆、知识库、工具结果或其他对话。固定提示不是防提示注入的安全边界；不执行工具才是本阶段的能力限制。
- 请求携带输出上限 1024 token，不指定温度。16 KiB 不是 token 数、上下文窗口保证或货币费用上限；未来适配器必须落实输出限制并验证模型支持情况。

## 持久化与幂等（仓储已实现）

独立回复请求表不把模型输出写入当前仅用户可写的消息表，也不改变现有 Redis 消息版本语义。首版不把历史回复重新注入上下文，页面创建确认中明确这一限制。

仓储在同一事务中校验所有者和对话存活，读取完整消息快照并调用规划器，冻结所选上下文、模型名称、配置版本及输出限制，同时预留一次额度。配置标识不允许包含密钥。唯一键为对话/请求 UUID，对话归属决定用户；同键同目标版本返回原请求，不同版本冲突。重放优先于当前消息版本、额度及服务端配置检查，因此新增消息或配置升级不改变旧请求。删除后的请求不能复活对话。

HTTP 创建要求 Cookie 会话和 CSRF，正文仅接受请求 UUID、目标消息版本；模型、系统提示和预算由服务端选择。内部 `Reply.context` 只供执行器使用，不返回浏览器。

状态采用 `queued → dispatching → succeeded / failed / unknown`，另有 `cancelled`。`claim_reply` 只允许 queued 领取一次；只有事务提交确认成功后，执行器才可发送。提交失败或响应未知不能推断自己已取得发送权。后续客户端、SDK、代理层必须关闭自动重试。

领取后期限固定 120 秒；`expire_reply` 将过期派发转为 unknown，完成操作也拒收超时结果。重复领取失败，终态完成重放不覆盖结果；未领取就完成返回冲突。成功输出限非空、无 NUL、最多 16 KiB。终态清空冻结上下文，仅成功保留回复正文。崩溃不会自动重新排队；过期扫描已接入后台，仓储查询本身不改变状态。

发送后超时、断线或进程崩溃可能已经计费，禁止自动重发。不能声称供应商“恰好执行一次”；保守策略可能在尚未真正发送时损失一次机会。用户再次尝试必须使用新请求并看到可能重复计费提示。

## 次数额度与取消（仓储已实现）

- 每用户每天（UTC，按预留日期）最多 20 次额度，每对话同时 1 个 queued/dispatching 请求；每对话累计最多 100 个请求（含取消），防止释放额度后无限积累记录。额度在 PostgreSQL 原子预留，进入 dispatching 后失败或未知也占用，只有未派发取消才释放，跨日取消退回原日期。不是按实际发送日期限流，也不是货币上限。
- 开启真实供应商前，必须补充模型专用输入计数、服务端价格配置及保守费用预留/结算；未配置或无法确认计费上界则禁止启用。具体货币额度由部署者明确设置，不在代码中假定价格。供应商返回 usage 仅供核对，不能靠响应后的统计阻止超支。
- 回复写入与对话删除统一按用户→对话行加锁，显式 READ COMMITTED；消息追加的对话锁也保护上下文快照。领取前取消阻止取得发送权，领取后取消丢弃晚到结果、不退额度；仓储不能中止供应商请求。取消终态只返回原状态，不撤销已完成回复。
- 删除对话同事务退回 queued 额度、取消未完成请求并清空全部上下文/输出。元数据随对话墓碑保留至少 24 小时，在后续创建触发墓碑清理时级联删除。次数账本仅含用户、日期和计数，不随对话清理，目前保留到用户删除，日账本归档后续实现。删除前已经读出的数据无法撤回，数据库备份/WAL 沿用部署保留策略。
- 回复页面按不可信纯文本展示，不自动调用工具、不提取长期记忆。货币预算及供应商启用仍未实现，不能据此开放付费调用。
